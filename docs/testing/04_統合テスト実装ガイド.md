## 2. 統合テストの概要

### 2.1 統合テストの目的

統合テストは、複数のコンポーネント、サービス、システム間の連携が正常に動作することを確認するテストです。

#### 主な検証項目
- **API連携**: Next.js フロントエンド ↔ App Router API Routes間の通信
- **データベース連携**: API Routes ↔ PostgreSQL (Prisma)間の操作
- **認証連携**: JWT認証による認証フロー
- **トランザクション**: 複数のDB操作の整合性確保
- **エンドツーエンド機能**: ユーザー操作から結果表示までの一連の流れ

### 4.1 App Router API テストの基本パターン

App Routerでは、Route Handlersを直接インポートしてテストします。

#### テストヘルパー関数

```typescript
// test/helpers/mock-request.ts
import { NextRequest } from 'next/server'

/**
 * NextRequestのモック作成ヘルパー
 */
export function createMockRequest(
  url: string = 'http://localhost:3000/api/test',
  options: {
    method?: string
    headers?: Record<string, string>
    body?: any
  } = {}
): NextRequest {
  const { method = 'GET', headers = {}, body } = options

  const defaultHeaders: Record<string, string> = {
    'content-type': 'application/json',
    ...headers
  }

  const requestInit: RequestInit = {
    method,
    headers: defaultHeaders
  }

  if (body && (method === 'POST' || method === 'PUT' || method === 'PATCH')) {
    requestInit.body = JSON.stringify(body)
  }

  return new NextRequest(url, requestInit)
}

/**
 * 認証付きリクエストの作成
 */
export function createAuthenticatedRequest(
  url: string,
  token: string,
  options: Parameters<typeof createMockRequest>[1] = {}
): NextRequest {
  return createMockRequest(url, {
    ...options,
    headers: {
      ...options.headers,
      authorization: `Bearer ${token}`
    }
  })
}
```

```typescript
import { describe, it, expect, beforeAll, afterAll, beforeEach } from '@jest/globals'
import { PrismaClient } from '@prisma/client'
```

```typescript
        testDataFactory.createEmployee(undefined, {

        })
      ).rejects.toThrow()
    })

  describe('論理削除テスト', () => {
    it('正常系: is_deletedフラグで論理削除', async () => {

      // 論理削除
      await prisma.employee.update({
        where: { id: employee.id },
        data: { is_deleted: true }

      const allEmployees = await prisma.employee.findMany({
        where: { id: employee.id }
      })

      expect(allEmployees).toHaveLength(1)
      expect(allEmployees[0].is_deleted).toBe(true)
    })
```

## 7. トラブルシューティング

### 7.1 よくある問題と解決策

| 問題 | 原因 | 解決方法 |
|------|------|---------|
| **データベース接続エラー** | PostgreSQLコンテナが起動していない | `docker-compose ps` で確認し、`docker-compose up -d postgres` で起動 |
| **Prismaマイグレーションエラー** | スキーマとDBの不整合 | `npx prisma migrate reset --force --schema=src/database/prisma/schema.prisma` でリセット |
| **テストタイムアウト** | テストが30秒以上かかる | jest.config.jsの`testTimeout`を増やすか、テストを最適化 |
| **ポート競合エラー** | 5434ポートが使用中 | `lsof -i :5434` で確認し、プロセスを停止 |
| **JWT_SECRET未定義** | 環境変数が設定されていない | `jest.setup.js` でデフォルト値を設定 |

## 8. ベストプラクティス

### 8.1 App Router対応テストの原則

1. **Route Handlers の動的インポート**
   - `import()` を使用してRoute Handler関数を取得
   - テストの独立性を保つ

2. **NextRequestのモック作成**
   - カスタムヘルパー関数を使用
   - 実際のHTTPリクエストに近い形でモック

3. **認証トークンの管理**
   - テストごとに新しいJWTトークンを生成
   - `generateToken()` を再利用

4. **Prismaトランザクション**
   - 複数操作は`$transaction`でラップ
   - エラー時の自動ロールバックを活用

### 8.2 テストデータ管理

1. **TestDataFactory パターン**
   - 一貫したテストデータ生成
   - 実際のスキーマに準拠したデータ作成

2. **クリーンアップ戦略**
   - `beforeEach` でデータクリーンアップ
   - `TRUNCATE CASCADE` を活用

3. **データ分離**
   - テスト専用データベースを使用
   - 本番環境との完全分離

### 8.3 アサーション推奨パターン

```typescript
// ✅ 良い例: 具体的なアサーション
expect(response.status).toBe(200)
expect(responseData.success).toBe(true)
expect(responseData.data).toHaveProperty('id')

// ❌ 悪い例: 曖昧なアサーション
expect(response.status).toBeTruthy()
expect(responseData).toBeDefined()
```
